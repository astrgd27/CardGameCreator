# Physical TCG compatibility audit — 2026-11-26

## Scope and evidence
Static design-gap audit of 25 physical collectible/trading card games, selected for market prominence or distinct mechanical architecture, not a sales ranking. Baseline: main d852a5c45f001db18e12252346e1b0d3682cf616 (PR #38 merged) plus candidate PR #39 at 719ed6bbd06d90b5d412f5b8c22dd1067a1bc89a (original head passed CI; reconciled head awaits its own run). The earlier 60-case catalog remains authoritative for measured coverage. No commercial game has been implemented or round-tripped in this audit; no case is promoted to a verified pass. Rules sources below are official hubs where possible; a few are accessible transcriptions. This is a mechanic-family review, not a card-by-card or comprehensive-rule-clause conformance certification. Publisher hubs were located, not every linked document exhaustively read.

Legend: E = existing primitive, P = partial/needs semantic work, G = missing general mechanism. E does NOT mean benchmark pass. All examples are design targets for original modules; no commercial assets or rules text copied.

## Cross-game gap backlog and acceptance
Ordered by dependency and reuse rather than popularity. A–H are implementation epics; split into focused PRs. Each requires original legal/illegal fixtures, deterministic replay, v2 validation/migration, graphical controls and private views where relevant. Counts below are references in the matrix, NOT coverage percentages.

- A — P0 action/payment primitives: data-driven play action binding source definition and selected instance; pre-commit mode/target/cost selection; multi-resource colored and hybrid costs, variable amount, resource-producing cards and ready/rest payments, threshold and cost modifiers; typed zone transitions. Acceptance: payment cancellation/rollback, no hidden identity leaks, dynamic source actions across two original decks. Do not hardcode game names.
- B — P0 card composition and deck roles: stack objects with ordered components, evolution/merge/inheritance, preserve identity/damage/attachment policy; typed main/extra/resource/leader decks, linked deck legality and opening policies. Acceptance: multiple deck components round-trip; illegal evolution rejected; component movement independent of UI.
- C — P0 hidden information and damage workflows: authorized temporary reveal/search/select/reorder and seeded random selection, per-viewer visibility, prize/security/life/check pipelines, optional trigger resolution, exhaustion conditions. Acceptance: unauthorized viewer never receives identity; canceled choices transactional; ordered reveal, deck exhaustion and nested choice fixtures.
- D — P0 configurable scheduler: automatic/optional phases, per-action alternation, initiative/pass-out, signed gauge handover after resolution, extra/skip turns, named response windows, APNAP and player-owned trigger order. Acceptance: deterministic event trace for alternating actions, gauge crossing with pending effect, nested reaction windows and cancellation.
- E — P1 combat and damage policies: configurable target categories, battle comparisons, defending from hand, typed damage, direct player/zone-card damage, variable assignment and trample, damage cleanup, guard/intercept, event payloads and last-known information. Acceptance: attack declarations through response and defeat; simultaneous loss; distinct combat policy fixtures for five primary games.
- F — P1 generalized continuous and state-based rules: typed attributes, bounded expressions and event bindings, multi-target iteration, status/counter conditions, layers with dependency resolution, non-damage replacements and choice ordering, state-based stabilization with cycle detection. Acceptance: conditional rule permissions change after source moves; invalid target fizzles without deadlock; state-based cascade terminates deterministically.
- G — P1 spatial board: named slots, occupancy, adjacency graph, grid and layers, movement costs and paths, line/circle positions, local targeting and control. Acceptance: slot legality, blocked path, zone-local combat, card stack visual and board navigation on tablet.
- H — P2 scoring, multiplayer and game policies: positive wins, objectives, score timing, persistent elimination/team rules and ties, asynchronous private selections where appropriate. Acceptance: score threshold, simultaneous objective scoring, elimination and two/four-seat scenarios.
- I — P0 cross-cutting authoring/verification: portable v2 ZIP asset bundle, module schema versioning and migration, data-only script capability documentation, typed layouts/cards, diagnostics, original benchmark fixtures. Maintain legacy standalone. Expand evidence catalog only via versioned mapping; preserve 60 original case IDs and gates. No release coverage claims before verified authoring/export/import/replay.

## Known implementation risks to address alongside epics
1. Current source-bound activation is available per instance but effect instructions often rely on fixed instance IDs; arbitrary replayable decks require dynamic source and target binding.
2. Resolution failure after a pending choice can strand a match. Distinguish invalid input from effect fizzle and provide explicit cancellation policy.
3. Player trigger ordering currently gives active player the entire batch; correct owner-specific order and FIFO/LIFO semantics must be designed.
4. Current token cleanup occurs after committed actions, not every intermediate event; attachments and references to removed objects need last-known information.
5. Stat auras can lower health without automatic lethal checks; modifiers/replacements may reference removed objects; use state stabilization.
6. Current strategic AI can inspect simulation outcomes beyond initial visibility and does not systematically search hidden-information beliefs; audit projection safety before expanding hidden actions.
7. Group combat is two-seat, once per turn, and damage assignment follows algorithms rather than arbitrary legal allocation. Combat resolution is a single blocking decision, not an extensible sequence.
8. Current generalized editor uses JSON and local storage separate from legacy ZIP workshop. Verify portable v2 export/import including artwork before marking any benchmark pass.
9. Current game examples are mechanics demonstrations, not balanced products. Establish original executable fixtures and human playtests.
